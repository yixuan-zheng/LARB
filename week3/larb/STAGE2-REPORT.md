# Stage 2: interrupt thinking without ending the response

October 16, 2026. Qwen3-4B on one PACE L40S per job.

## Answer to the engineering question

**Yes: we can interrupt the designated thinking phase and keep the same response running.** A controller forced the closing `</think>` token after 512 pre-close tokens. All ten requests continued generating afterward, using the existing KV cache inside the same `generate` call.

However, closing the marker does not always make the model finish its reasoning or answer promptly. Seven requests ended normally; three continued until their separate answer cap. A short finalization cue improved completion on a focused three-case follow-up, but one of those completed answers was wrong.

The mechanism works well enough for the next preliminary budget comparison. A 512-token budget is not yet a validated quality-preserving setting.

## What we implemented

1. Use the same pinned checkpoint, prompts, sampling settings, and seeds as Stage 1.
2. Generate normally until the thinking budget is reached.
3. Force a transition through a logits processor. Do not emit an end-of-response token.
4. Release control and allow normal answer generation, with a separate 2,048-token allowance.
5. Record the transition, continuation, completion status, correctness, and timing.

The budget uses Stage 1's count convention: 512 generated tokens before the closing marker, including the opening marker and whitespace. It is not 512 English words or exactly 512 content-only thinking tokens.

The controller does not restart the request, replay the prefix, inject a reference answer, or change the original user prompt. All pre-cutoff token prefixes matched Stage 1 exactly. The GPU experiments use one request at a time; concurrent serving integration has not been tested.

For context, Qwen's [thinking-budget guide](https://qwen.readthedocs.io/en/v3.0/getting_started/thinking_budget.html) also uses an explicit closing boundary and a continuation step. Our implementation applies its transition in place within a single generation call.

| 10 | Parenthesization values | 2,048 | 55.94 | Answer cap; no boxed final answer |

Mechanical checks:

- **10/10** closing markers at exactly token index 512, following 512 pre-close tokens.
- **10/10** nonempty continuations after closure.
- **10/10** pre-cutoff prefixes match Stage 1.
- **0/10** reopened `<think>` markers.
- **7/10** normally completed, correct responses.
- **8/10** contain a correct boxed answer, including the incomplete angle response. We retain that distinction rather than counting it as a clean completion.

The double-sum and angle outputs show reasoning and self-checking continuing outside the thinking tags. No reopened marker is needed for that behavior. Thus, marker closure alone is not a guarantee that reasoning has stopped.

Median generation time was **22.48 seconds**, compared with **79.26 seconds** in Stage 1. This is descriptive: completion rates differ, and Stage 2 adds per-token synchronization for instrumentation. It is not a quality-matched serving-speed result.

The median observed delay from the controller trigger to the forced closing token was **1.29 ms**. This measures the local token-forcing step, not an external control API or user-visible response latency.

## Test B: finalization cue, then closing marker

Job `6306428`, three selected problems: one successful control, the double-sum failure, and Stage 1's long-running parenthesization failure. This is a targeted engineering follow-up, not a second ten-problem evaluation. The angle problem was not retested with this cue.

After 512 normal tokens, force this fixed transition text:

```text


I will stop checking and give the final answer now.
</think>

```

The cue is controller-injected text, not reasoning independently generated by the model. It occupies 14 tokens total; 12 appear before the closing token. Therefore the recorded closing index is 524, while the normal model-generated pre-transition allowance remains 512. The extra tokens and their execution time are included in the results.

| Problem | Tokens after closure | Time (s) | Result |
| --- | ---: | ---: | --- |
| 1: Polar coordinates | 312 | 18.52 | Correct; normal completion |
| 2: Double infinite sum | 703 | 26.79 | Correct `p - q`; normal completion |
| 10: Parenthesization values | 714 | 27.05 | Wrong `14`, reference `4`; normal completion |

All three preserved their Stage 1 prefixes and returned boxed final answers with normal end-of-response tokens. None reopened a thinking block. The double-sum case stopped looping and finalized correctly. The parenthesization case finalized but confused the number of parenthesizations with the number of distinct values.

This is **3/3 successful response completions and 2/3 correct answers** on selected development cases. It is not evidence that the cue meets an accuracy floor. The median trigger-to-closing-token observation delay was **263 ms**, including execution of the injected cue. Post-close counts include the injected trailing newline.

## What to carry forward

Keep the in-place controller and separate answer allowance. Use the cue variant as the next candidate, with the bare closing marker retained as a control. The next preliminary test should compare a few thinking budgets on a larger fixed development set and score both normal completion and correctness.

Do not build load adaptation yet. First check whether any budget and transition combination saves time while retaining useful accuracy. Answer text can still contain extended reasoning, so the answer allowance must remain explicit and answer-cap failures must remain visible.
