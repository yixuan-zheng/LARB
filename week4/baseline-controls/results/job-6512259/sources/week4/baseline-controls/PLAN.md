# Focused fixed-budget serving comparison

Frozen before new inference, 2026-10-24. This is development work, not another held-out evaluation. It asks whether shortening every request to 2,048 or 4,096 thinking tokens matches the useful deadline/quality tradeoff of unchanged live LARB.

Four policies share one engine per allocation: fixed2048, admission, live, fixed4096; block 1 reverses that order and rotates the question positions by six. The 12 questions are the smallest SHA-256 ranks of `week4-fixed-controls-v1:INDEX` over exposed indices 0–99 excluding calibration 0/2. No answers or generated lengths determined this selection. Exact indices are in plan.json. The original 24-question 5B cohort and other 376 questions are not used.

Late burst and sustained pressure retain the 5A arrival/deadline rules with fresh exposed-only calibration 0/2 in each allocation, frozen numeric traces before measurement, fixed per-job horizons and phase drains. There are 96 outcomes per condition, 192 total, on 12 unique questions. Gate results (24 outcomes on known exposed indices 1/4/5) and six calibration requests across three GPU allocations are excluded. Gates require actual concurrency and a complete uncapped forced transition in each fixed mode, irrespective of correctness.

Same pinned Qwen3-4B, BF16, vLLM 0.11.2, H100 80GB, two active sequences, stock scheduling, prefix cache off, temperature .6/top-p .95/top-k20, seed 6222+index, original cue and separate 2,048 answer allowance. Fixed modes never change their selected thinking budget. Original admission/live functions and serving adapter/server behavior are preserved; the new isolated policy module only extends static choices.

Compare live against each static alternative separately for correct-and-normal final answers received before deadline. Report eventual correctness per condition/block, failure/cap counts, paired changes, latency including failures, queue time, all output tokens and cutoff events. Do not select a favorable fixed budget, suppress failures, or pool rates across unrelated calibrated horizons. These repeated development observations support diagnosis, not a population accuracy guarantee. Equal overall correctness does not erase individual or condition-specific losses.

CPU preflight (20-minute ceiling) verifies all deployed sources and grader imports and reproduces a saved real-result grade. Then one GPU gate (2-hour ceiling), burst comparison (4 hours), and sustained comparison (4 hours) run serially after-success. GPU driver limits are 110/230/230 minutes, engine readiness allowance 25 minutes and phase allowance 45 minutes. Runtime-fit checks precede measurement. Expected actual GPU use is roughly 2–4 hours; maximum base allocation is 10 GPU-hours. No automatic retries or extra repair allocations are authorized by this plan.

Each GPU job exits successfully only after complete raw coverage, mechanical/provenance audit and lossless event archiving. The gate additionally runs the actual grader. Caps/wrong answers in comparisons remain scientific outcomes and do not halt later conditions. Infrastructure failure halts downstream inference and cancels invalid dependencies. A CPU finalizer (30-minute ceiling) runs after all GPU stages terminate, including cancellation, grades successful stages and writes an explicit complete/partial report. It needs no local observer or open chat. It never submits new inference. Analysis and raw evidence remain in this folder on the prepared cluster; sanitized collection to Git is a later read-only step.

The next scientific step is diagnosis of useful versus unnecessary cuts, not an automatic heuristic sweep, LASER implementation, deadline-guard run, or new validation campaign.
