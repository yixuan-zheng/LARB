# Adaptive reasoning follow-up · proposal for review

Historical design record. The 96-question fallback completed. See the [research narrative](RESEARCH-NARRATIVE.md) for the executed recipe and results.

The first screen reached 60.6% at 6,757 charged tokens per request, below the fixed-mode mixture at the same cost (63.7%) and the shuffled router (61.6% at 6,627 tokens). A hindsight allocation preserved the 22 High successes while reducing charged tokens from 239,093 to 106,249 across 33 questions. That 56% is single-draw headroom from observing all outcomes before choosing. It also includes saving tokens on High failures. The follow-up asks whether an outcome-trained model can capture any meaningful fraction of that opportunity on a more varied workload.

## Recommended run

1. **Freeze the data.** Draw training and development questions from GSM8K train, MATH train, and a pinned, verified short-answer Omni-MATH pool. Target a 1:1:1 source mixture in training. Use MATH-500 and disjoint GSM8K and Omni-MATH questions for evaluation. Remove exact and near duplicates across sources and exclude previously inspected evaluation questions from the new held-out set. Strip dataset labels from prompts. Choose 48 development questions and 192 held-out questions, evenly divided by source. Check reference parsing before freezing. Audit mode behavior on development with repeated fixed-mode outcomes and include easy, salvageable and low-success questions. Freeze an unselected source-stratified evaluation set so outcome screening does not inflate headroom.
2. **Train a three-mode generation policy.** Use the pinned Qwen3-4B checkpoint and existing Low/direct, Medium/2,048 and High/8,192 reasoning contract with the shared answer allowance. Reuse the validated delimiter injection, training masks, verifier and checkpoint code. Scale to 64 optimizer updates with eight distinct questions per update and eight rollouts per question (512 groups, 4,096 rollouts). Use eight rollout draws with two forced per mode and two free during the first 16 updates. Then use all free draws and anneal the balance term to zero before the final checkpoint. Use verifier-based mode-discounted rewards and group mean centering. Keep forced warm-up explicitly separate from on-policy training. During free training, store behavior log probabilities under the actual masked sampling distribution, exclude environment-forced tokens from the loss, and verify they match recomputed probabilities before the first update. Save checkpoints every eight updates and predeclare the checkpoint selection rule on development only.
3. **Close the methodological gaps.** The published three-mode study used 90 updates, 128 prompts per update, eight rollouts, four H100s, and three training seeds. Its response-length masks and uncapped evaluation differ from LARB's enforced reasoning-only caps. Our first run had 22 updates on 24 training questions, one question per update, restricted root actions and one training seed. The proposed run retains the restricted three-action set and LoRA, improves group diversity and free-policy training, and uses the same capped contract at training and evaluation. It remains a smaller adaptation. Use one primary training seed and a separately authorized second seed only to confirm a promising result. [Learning When to Think](https://arxiv.org/html/2608.20256)
4. **Evaluate once on sealed questions.** Collect two paired draws per question for each same-checkpoint fixed mode. Evaluate free routing with the same sampling contract and verify end-to-end parity against forced-mode replay on a small prespecified subset. Include a compute-matched fixed mixture, global shuffle, within-source shuffle, and a cheap source/length baseline calibrated on development. The within-source control tests whether the router adds value beyond identifying the dataset. Include an untrained-mode comparison on development to separate solver improvements from routing gains. Report overall and per-source accuracy, mode mix, cap hits, realized tokens including routing overhead, and GPU time on a matched execution profile. Group uncertainty by question and keep both draws together. Report the hindsight oracle only as a retrospective reference.

## GPU budget and timeline

The prior HF job took 6h 37m for 132 training rollouts and 99 forced evaluation solves. At that end-to-end rate, scaling the same backend directly would take well over 100 GPU-hours. Use batched vLLM rollouts and evaluation with LoRA snapshots and a separate PyTorch trainer. The underlying contracts and scorer are already validated. Adapter parity and behavior-log-probability agreement on the batched backend still need verification.

These estimates use approximately 1,000–2,000 generated tokens per rollout and the earlier measured 244 output tokens/s from standalone vLLM. The rate with refreshed LoRA snapshots is unmeasured. Budget for 8 CPUs and 32–64 GB RAM per GPU, node-local rollout files and retained checkpoints in shared storage. Cap the initial parity and throughput gate at 60 minutes, charge it to the chosen allocation, and reserve the last third of the job for evaluation and export. Stop before training if the measured rate or queue leaves insufficient time. The recommended run needs an explicit extension beyond the November 25 cutoff if a suitable block cannot be secured with the evaluation window intact. Under a firm cutoff, consider the reduced run only with a confirmed slot, a passing backend gate and guaranteed evaluation time. Serving scaling keeps its own resources, code path and decision schedule.

## Decision

Advance only if adaptive routing uses **at least 10% less measured inference compute at comparable accuracy** against the same-checkpoint fixed mixture, with a positive paired advantage over shuffled routing and no major source-specific regression. Prespecify comparable accuracy as a point loss of at most 2 percentage points and report the paired interval. A positive point estimate with a wide interval earns confirmation, rather than a serving integration claim. A valid null closes this recipe for the project timeline. An engineering or scheduling stop is reported as unevaluated, with the checkpoint and completed evidence preserved.

If full-trajectory updates are the measured bottleneck, a separately labeled three-action adaptation of root-token policy optimization is a fallback. It can reduce backward cost while keeping full rollout costs. Its original evidence is for binary branching and it answers a narrower question. [Root-token Policy Optimization](https://aclanthology.org/2026.acl-long.816/)
